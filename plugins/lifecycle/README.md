# lifecycle 2.0.0

Quick, Standard and High-risk delivery workflows with scoped planning, exact-candidate verification and authorized release actions.

Install declared dependencies. Load only relevant skills/resources; required availability is not a recursive workflow.

| Skill | Purpose |
|---|---|
| [bootstrap-project](skills/bootstrap-project/SKILL.md) | Set up a new repository so agents can build it safely from day one — create the repo and an initial commit, protect main, set up the tracker (milestones, labels, templates) and a bootstrap issue, then on its branch record the stack decisions, build a walking skeleton (one request end to end, one scheduled job when the product needs one, deployed to a test environment), write AGENTS.md with the real commands, safety-critical paths and rules, install the placement table and allowlist architecture tests with reviewed legacy baselines with no new violations, lint/format, CI on hosted runners, and open the PR that closes the issue. Covers web and mobile setup. Use after shape-idea, or when an existing repo has no agent rules, conventions or CI. Trigger on /bootstrap-project, 'set up the repo', 'start a new project', 'scaffold the app', 'add AGENTS.md', 'make this repo agent-ready'. |
| [bugfix](skills/bugfix/SKILL.md) | Fix a bug end to end — reuse or run the investigation (reuse existing task context; preserve uncertainty when the cause is unverified), risk-appropriate design review, a permanent regression test that fails before for the reported reason and passes after, fix the root cause not the symptom plus the 'why was it breakable' guard, blast radius (same pattern, other platform, stored data repair, installed old versions), verify, then PR with the failure mode explained. Trigger on /bugfix, 'fix this bug', 'fix issue', 'make this test pass', 'implement the fix', 'hotfix'. |
| [ci](skills/ci/SKILL.md) | Drive a pull request through continuous integration and debug failures — ship (watch the checks on the head commit to green, never re-run to get past a real failure), debug (find the first error, classify it, reproduce locally with the same command, fix the cause), optimize (measure the slowest steps over three runs), and change workflows safely (stable job names the merge gates refer to, pinned actions, no secrets in files, never a self-hosted runner on a public repository). Use when a PR is waiting on CI or CI is red. Trigger on /ci, 'watch CI', 'why is CI red', 'CI is failing', 'fix the build', 'is my PR green', 'speed up CI', 'add a workflow'. |
| [cleanup](skills/cleanup/SKILL.md) | Tidy up after a pull request is merged or abandoned — confirm its state, close or update the issue and the epic checklist, delete the local and remote branch, remove the worktree from another checkout, and stop local services, emulators and dev servers started for the work, without touching other projects' containers or a shared stash. Use when a PR is merged or a branch is dead. Trigger on /cleanup, 'clean up', 'PR is merged, tidy up', 'remove the worktree', 'delete the branch', 'stop the services'. |
| [create-pr](skills/create-pr/SKILL.md) | Open a pull request the reviewer can trust — preconditions, reuse an existing PR, appropriate issue linkage without mandatory tracker ceremony, bring the branch up to date, collect real evidence first (command outputs, screenshots with synthetic data, the design review link, device tests listed as open), write a per-area description with safety and privacy notes, push and open on the user's go-ahead, then get an independent code review posted on the PR and fix critical and major findings before CI and merge. Use when the work on a branch is ready for review. Trigger on /create-pr, 'open a PR', 'create the pull request', 'push and open a PR', 'raise a PR', 'send this for review'. |
| [deploy-check](skills/deploy-check/SKILL.md) | Pre-merge scan of a change for what breaks real users after it is deployed — non-additive API contract changes that installed clients still call, migrations that rewrite or lock big tables, native or bridge changes that need a store release, new permissions, background behaviour, push payloads, configuration and secrets per environment (including trusted-proxy settings and tokens in URLs), realtime method names, feature flags, rollback, and major dependency bumps — with a verdict, deploy order and rollback plan. Use before merging anything that touches an API, data, native code, config or infrastructure. Trigger on /deploy-check, 'is this safe to merge', 'breaking change check', 'will this break old app versions', 'pre-merge check', 'deploy order'. |
| [design-review](skills/design-review/SKILL.md) | Review consequential design decisions, risks and verification before expensive work. Use for high-risk plans, costly-to-reverse choices or an explicit architecture review; do not impose a separate review on every small change. |
| [engineering-principles](skills/engineering-principles/SKILL.md) | Choose cohesive architecture and justified abstractions for the actual product. Use when deciding placement, reviewing design, applying SOLID or reducing complexity; adapt to project constraints rather than impose one architecture. |
| [feature-to-issues](skills/feature-to-issues/SKILL.md) | Break an approved spec into an epic with sub-issues — vertical slices a person can use end to end, ordered riskiest first (safety and technical risk, then dependency, then learning, then the rest), spikes for research, every must requirement and every safety failure mode owned by a slice, priorities from must/should/could — shown in full for approval before anything is created, then created and linked, and a manifest saved. Trigger on /feature-to-issues, 'break this into issues', 'create the issues for this feature', 'make an epic', 'create sub-issues', 'slice this spec'. |
| [file-bug](skills/file-bug/SKILL.md) | Record a bug as an issue with a fixed template — symptom-style title, observed vs expected (citing the spec or design), steps to reproduce from a fresh state, environment, frequency, severity mapped to priority (P0 when a safety-critical path can fail silently, data is exposed or lost), safety impact, evidence with personal data stripped, suspected cause labelled as a theory, and the regression test to add — after the owner's approval, linked to its epic. Trigger on /file-bug, 'file a bug', 'log this bug', 'create a bug issue', 'report this as a bug'. |
| [file-feature](skills/file-feature/SKILL.md) | File one already-scoped feature slice as an issue with a fixed template — outcome-style conventional title, design frame, MVP id and milestone, priority, areas and flags (safety-critical, privacy, needs-device-test), what and why, 3–7 checkable acceptance criteria including failure states, tests to write first, approach, out of scope, open questions — after a privacy check and the owner's approval; optionally attached to an epic. Trigger on /file-feature, 'file this feature', 'create an issue for', 'open a feature issue', 'track this as an issue'. |
| [implement](skills/implement/SKILL.md) | Implement a feature, fix or maintenance change with proportionate planning and verification. Use for authorized code changes; preserve existing work and load only affected specialist guidance. |
| [incident](skills/incident/SKILL.md) | Handle a live production problem — declare severity in the first minutes (SEV1 when people may be unsafe or data is exposed or leaked, SEV2 when a core flow is broken, SEV3 when degraded), stop the harm first (halt the rollout, roll back, switch a flag off, cut a leaking endpoint), keep a timeline, draft communication for the user's OK, investigate read-only, fix through the normal bugfix path, verify recovery with the same signal that showed the problem, and hand off to a postmortem. Use when something is broken for real users. Trigger on /incident, 'prod is down', 'users can see other users data', 'payments failing', 'notifications not arriving', 'emergency', 'everything is broken', 'outage'. |
| [investigate-bug](skills/investigate-bug/SKILL.md) | Find the root cause of a bug — reproduce it first with a failing test or on a device (on a fix branch linked to the bug issue), pin the symptom, keep evidence-backed competing hypotheses with facts and theories apart, narrow with code history, logs, error tracker and read-only data, drive to the deepest cause in our control with causal analysis, measure the blast radius, and write the report including how to prevent the whole class. Trigger on /investigate-bug, 'why is this happening', 'root cause this', 'dig into this bug', 'figure out what is wrong', 'this stopped working', 'debug this'. |
| [investigate-feature](skills/investigate-feature/SKILL.md) | Investigate a feature before anyone specs or builds it — read the design, the product brief and MVP scope, and the existing code; map people, states (or a state table and low-fidelity flow when there is no design), data, API, platform/background work, battery, safety failure modes, privacy, analytics, performance and dependencies; keep facts (with sources) apart from assumptions; produce a build pack with options and open questions. Use before spec or file-feature for anything not already scoped. Trigger on /investigate-feature, 'investigate this feature', 'what does feature X need', 'research this feature', 'how should we build X', 'discovery for'. |
| [merge](skills/merge/SKILL.md) | Check exact-candidate merge eligibility and merge only when authorized. Use when asked to assess readiness or merge a PR; explicit no-merge instructions always stop before mutation. |
| [new-feature](skills/new-feature/SKILL.md) | Deliver a feature with a risk-based workflow and relevant verification. Use when asked to build a feature end to end; route small changes directly and reserve separate specifications/reviews for justified risk. |
| [observe](skills/observe/SKILL.md) | Answer health questions from production signals, or add the signals a change needs so someone finds out about a failure before a user does — pin the window, read errors, metrics, traces and logs, compare with a baseline, keep facts apart from theories; when adding signals, errors reach the error tracker, metrics use low-cardinality tags with no personal data, traces wrap hot paths and outbound calls, logs follow the privacy logging rule, every safety signal gets an alert rule and an owner, and a test proves the signal fires on the failure path. Use after a release, when something looks slow or broken, or while building a new failure mode. Trigger on /observe, 'is the release healthy', 'why is it slow', 'error rate', 'add metrics', 'add monitoring', 'add an alert', 'instrument this'. |
| [postmortem](skills/postmortem/SKILL.md) | Write a blameless postmortem after an incident or any bug where a critical alert was missed or data was exposed — summary, impact, UTC timeline, root cause by five whys, detection (which rung of the testing-doctrine ladder caught it and which should have), what went well, badly and lucky, and follow-ups that prevent, detect earlier or mitigate, each with an issue — then update the skills that would have caught it. Use after SEV1/SEV2 incidents and serious escapes. Trigger on /postmortem, 'write the postmortem', 'incident review', 'what did we learn', 'retro on the outage', 'root cause analysis document'. |
| [pre-commit](skills/pre-commit/SKILL.md) | Check the working tree and commit it safely — not on the main branch, named paths staged only, secrets and personal-data scan, generated code in sync with its source, only touched files formatted, the project's lint/analyze/test run for each changed area, a safety-critical check, and a conventional commit that follows the project's author and attribution policy. Never bypasses hooks. Use when about to commit. Trigger on /pre-commit, 'commit this', 'check before committing', 'is this ready to commit', 'stage and commit'. |
| [release](skills/release/SKILL.md) | Ship merged work to users safely — decide the release path per component (backend deploy, web deploy, over-the-air patch where the stack supports it, or a store release for native code, permissions and new plugins — the default depends on the client), check preconditions, version and tag with the user's OK, roll out in stages with an OK and a watch window per step, watch health signals, and roll back per path when a safety or health signal regresses. Use when merged changes should reach users. Trigger on /release, 'ship it', 'release a new version', 'cut a release', 'hotfix', 'staged rollout', 'roll back the release', 'publish to the store'. |
| [shape-idea](skills/shape-idea/SKILL.md) | Turn a raw product idea into a short product brief and an MVP scope — problem and users, the riskiest assumptions, what success looks like, the smallest useful product, features grouped into ordered milestones with acceptance-level outcomes, what is out of scope, and the open questions only the owner can answer. Use at the very start of a new product or a big new area, before any stack choice or code. Trigger on /shape-idea, 'I have an idea', 'new app idea', 'what should the MVP be', 'scope this product', 'plan the milestones', 'product brief'. |
| [spec](skills/spec/SKILL.md) | Write and get approval for a feature spec — problem and users, designs and states, numbered must/should/could requirements with checkable acceptance criteria, API contract with who may call what, data and migration risk, client and platform/background behaviour, safety failure modes and privacy rules each becoming criteria, analytics, performance budgets, rollout and rollback, risks and open questions — reviewed by a fresh agent and always design-reviewed by the architect agent before approval. Use for anything multi-area, schema-changing, safety-critical or privacy-relevant. Trigger on /spec, 'write a spec', 'spec this feature', 'PRD', 'technical design for', 'plan this feature'. |
| [start-issue](skills/start-issue/SKILL.md) | Prepare an issue or direct task with an isolated branch, current context and risk-appropriate plan. Use when starting implementation; an issue is required only by the project or requested workflow. |
