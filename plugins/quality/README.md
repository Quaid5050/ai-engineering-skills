# quality 2.0.0

Testing doctrine, TDD, writing tests, code review with a separate design pass, security and privacy review, accessibility audit, performance checks, static catalogs (one row per case instead of repeated switches) and privacy-safe product analytics. Framework-agnostic, with stack references.

Install declared dependencies. Load only relevant skills/resources; required availability is not a recursive workflow.

| Skill | Purpose |
|---|---|
| [accessibility-audit](skills/accessibility-audit/SKILL.md) | Audit a screen, page, feature or PR for accessibility against WCAG 2.2 AA, on web and mobile — automated checks added to the tests (labels, tap targets, contrast), a text-scaling test to 200%, manual checks (screen-reader labels and order, state not by colour alone, contrast per token pair, targets, reduced motion, time limits, sound/haptics, right-to-left, error announcements) and a screen-reader pass on a real device. Use for UI-heavy changes and before release. Trigger on /accessibility-audit, 'accessibility check', 'a11y review', 'is this accessible', 'screen reader', 'contrast check', 'WCAG'. |
| [analytics-event](skills/analytics-event/SKILL.md) | Add or change a product analytics event, or answer a product question from events, without collecting personal data — first-party pipeline preferred, the product question first, object_action names, allow-listed properties only (never location, free text, contact details or raw user ids), pseudonymous ids hashed server-side with a secret, consent honoured, the event catalogue as the single source of truth, tests that the exact event is sent and nothing is recorded when analytics is off, cohort queries for questions. Use when someone wants to measure usage. Trigger on /analytics-event, 'track this', 'add an analytics event', 'measure adoption of', 'how many people use', 'funnel for', 'retention of'. |
| [code-review](skills/code-review/SKILL.md) | Review a diff or PR on any stack — shape first, then every applicable dimension (safety-critical paths, privacy and tenant isolation, tests you can trust, correctness, contract, data, platform and battery, design and UX, performance, observability, simplicity, layer placement, conventions, repo hygiene), then a risk-appropriate design assessment (placement, duplication across features, reuse, technical code out of business layers, validation/secret/storage homes, design review posted before code). Each finding has severity, file:line, failure scenario, fix and the rung where it should have been caught; plus a merge risk tier. Use before every merge. Trigger on /code-review, 'review this', 'review the PR', 'review my changes', 'check the diff', 'is this ready to merge'. |
| [perf-check](skills/perf-check/SKILL.md) | Measure a screen, page, endpoint, query, background task or PR against the project's performance budgets and fix what is over — pick or write the budget first, measure a baseline in release/profile mode on the reference device or environment (3+ runs, median), find the cause with a profiler, change one thing, measure again the same way, guard it with a test or CI threshold, report before and after. Covers app startup, jank, memory, size, battery, web vitals, API latency, slow queries and N+1. Use when a change touches a hot path or something feels slow. Trigger on /perf-check, 'is this fast enough', 'performance', 'slow endpoint', 'slow query', 'jank', 'battery drain', 'app size', 'load test', 'N+1'. |
| [security-privacy-review](skills/security-privacy-review/SKILL.md) | Review a change, spec or feature for how it could expose someone's personal data or be abused — map every piece of personal data (created, stored, sent, who reads it, kept how long), check authorisation and tenant isolation with forbidden-caller tests, consent and visibility, abuse cases by insiders and controlling people, leaks into logs/errors/telemetry/analytics (the canonical logging rule), uploads and metadata, secrets per purpose, an OWASP API Top 10 pass, retention and deletion. Use when a change touches personal data, auth, sharing, payments, uploads, exports or a new third-party SDK. Trigger on /security-privacy-review, 'security review', 'privacy review', 'threat model this', 'can this leak', 'is this safe', 'abuse case'. |
| [static-catalogs](skills/static-catalogs/SKILL.md) | Turn a closed set the app defines itself (languages, plans, providers, modes, built-in commands) into one table, one row per case holding every attribute, instead of the same switch repeated per attribute. Decide whether a data file plus code generation is justified (only when the source of truth lives outside the code or is shared across apps), pin today's values with characterisation tests, migrate without changing behaviour, and guard it. Use when adding one case means editing several places, or when someone proposes moving enums to a config file or codegen. Trigger on /static-catalogs, 'same switch everywhere', 'move this to YAML', 'should we codegen this', 'config file for enums', 'single source of truth', 'add a language', 'add a provider'. |
| [tdd](skills/tdd/SKILL.md) | Build a behaviour test-first, one test at a time — pick the next behaviour from the test list, write one failing test and see it fail for the expected reason, write the least code to pass, refactor while green, commit, repeat; with the signals that mean the design is wrong and the few allowed exceptions. Use when implementing any behaviour change. Trigger on /tdd, 'test first', 'red green refactor', 'TDD this', 'write the failing test first', 'build this test-driven'. |
| [testing-doctrine](skills/testing-doctrine/SKILL.md) | Choose meaningful tests by risk, boundaries and observable invariants. Use when writing or reviewing tests, investigating flakiness or planning verification; includes property, sequence, integration and failure-path testing. |
| [write-tests](skills/write-tests/SKILL.md) | Write the tests for a file, feature, behaviour or diff in this project — list every behaviour (happy, variations, edges, errors; safety failure paths first), pick the lowest level that proves each (unit, integration through the real entry point, UI per state, platform), write them to the testing doctrine, run the single test, then the area, and report red/green evidence and break-it checks. Stack references for common test toolchains. Use when adding tests to new or existing code. Trigger on /write-tests, 'write tests for', 'add tests', 'test this', 'cover this with tests', 'what tests are missing'. |
